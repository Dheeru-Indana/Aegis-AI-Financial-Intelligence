## 1. Actual System Architecture

AegisAI is a financial intelligence and fraud detection platform operating a dual-tier architecture:

```
[Browser / Client (React 19 + TypeScript + Vite)]
   │
   ├─► [Supabase Backend (PostgreSQL + PostgREST + Auth + Realtime)]
   │     • Tables: public.profiles, public.transactions, public.cases, public.risk_rules, public.audit_logs
   │     • Channel: realtime_transactions (postgres_changes INSERT)
   │
   └─► [Python ML Model Service (FastAPI + scikit-learn Logistic Regression)]
         • Port: 8000
         • Artifact: ml/artifacts/active_model.joblib (v2.0.0, 3.8 KB)
         • Inference: /api/score, /api/score/batch
         • Diagnostics: /health, /model/info, /metrics/summary
```

### 1.1 Client Runtime Architecture
- **Framework:** React 19 SPA running on Vite, TailwindCSS (utility classes), Vanilla CSS design system (`src/styles.css`).
- **State Management:** React Context (`AuthContext` for session/role caching) + top-level state in `App.tsx` coordinating views, active filters, transactions, cases, rules, and audit logs.
- **Client Fallback Intelligence:** If the Python model microservice is unreachable, `src/services/modelScorers.ts` provides an exact mirror implementation (`TrainedMLScorer`) trained with canonical weights matching `v2.0.0` ensuring deterministic offline operation.

## 3. Data Sources & Provenance Model

To prevent synthetic or demo fixtures from contaminating real banking operations, the system enforces a strict 6-tier taxonomy:
1. `live`: Incoming transactions from verified banking/payment integration or webhook.
2. `imported`: Authenticated CSV file uploads processed through the validated ingestion pipeline.
3. `demo`: Pre-configured demonstration fixtures clearly labeled for walkthroughs.
4. `simulation`: Synthetic load generated by Attack Digital Twin or stress tests.
5. `test`: Isolated fixtures created during automated unit/integration test runs.
6. `unknown`: Records lacking cryptographic or verifiable pipeline origin.

## 4. Root Causes of Connection & Status Inconsistencies Discovered

### 4.1 "CONNECTION ERROR" Banner vs "Realtime Stream: Live" Discrepancy
- **Root Cause 1 (RLS 403 on Health Check):** `src/lib/supabase.ts` `checkSystemHealth()` executed `supabase.from("profiles").select("id").limit(1)`. When unauthenticated or before session restoration, PostgREST returned HTTP 403 `permission denied for table profiles` because the table's default policy restricts anonymous reads. This caused `dbHealth.database = "disconnected"` and raised the red banner.
- **Root Cause 2 (Decoupled Realtime Indicator):** In `src/App.tsx`, the top bar and `Transactions` header checked `isConfigured ? "Realtime stream" : "Simulated stream"`. It evaluated whether `VITE_SUPABASE_URL` was configured in `.env`, rather than the actual socket connection status of `channel.subscribe((status) => ...)`.
- **Repair:**
  1. Updated `checkSystemHealth()` to probe a readable public catalog or execute with authenticated user session.
  2. Bound the Realtime status badge strictly to the channel subscription callback (`SUBSCRIBED` $\to$ Connected; `CLOSED` / `CHANNEL_ERROR` $\to$ Disconnected).
  3. Added an explicit data source/provenance filter.

### 4.2 Administrator Access Loss
- **Root Cause:** PostgreSQL trigger `check_profile_role_update()` prevented client-side updates to `role` without existing admin privileges. During registration or profile recreation, the account defaulted to `analyst`.
- **Repair:** Admin role recovery procedure provided via `bootstrap_admin.sql` updating `auth.users.raw_app_meta_data`, `public.profiles.role = 'administrator'`, and verified client-side in `AuthContext` by reading both metadata and database record.
